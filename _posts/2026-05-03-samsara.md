Samsara is an attempt at building an [open-ended](https://www.youtube.com/watch?v=OLi0eIdyQU4) game engine.

Coding agents are now good enough to generate massive amounts of code, port subsystems (like terrain generation), oneshot gpu kernels, and set up training loops. The engine increasingly matters more as they get stronger. If agents are going to help build games, they need a world they can operate on, a way to see what happened, and a way to replay the same situation after a change.

Games are the closest we currently have to the ultimate testbed: A small ruleset can unfold into skill, geography, conflict, and history. [Cellular automata](https://en.wikipedia.org/wiki/Cellular_automaton) show a minimal version of this: local rules producing global behavior. [Busy Beaver](https://en.wikipedia.org/wiki/Busy_beaver) asks how much behavior a tiny program can produce before halting. Games add interaction (and taste) to that question.

The space of possible games has a similar flavor to Busy Beaver. While most of the space is trivial or boring, you can find small rule systems that unfold into ridiculous amounts of interesting structure. The hard part is finding them: Kenneth Stanley and Joel Lehman's work around [Picbreeder](https://nbenko1.github.io/picbreeder/), [novelty search](https://www.cs.swarthmore.edu/~meeden/DevelopmentalRobotics/lehman_ecj11.pdf), and [the myth of the objective](https://books.google.com/books/about/Why_Greatness_Cannot_Be_Planned.html?id=Llb1CAAAQBAJ) or [ASAL](https://sakana.ai/asal/) are extremely interesting places to look into. Machines can generate variations quickly, but humans still matter where variation has to become taste.

The phrase [operational latent space](https://arxiv.org/abs/2406.02699) is useful here. You encode games by their genotype: map generation, combat rules, resource systems, policies, etc in order to produce an interesting phenotype. An interpolation between two genotypes should decode into a meaningful intermediate phenotype (i.e. game) that feels like a proper remix of the two. One direction can turn the game into something more territorial, while another makes cooperation more valuable. The latent becomes operational when operations inside it survive decoding back into the actual game.

I started with voxels because they give a useful algebra of matter. Minecraft is the obvious reference point: It found a really well-compressed grammar of blocks, terrain, tools, inventories, etc. From that grammar came economies, monuments, [2b2t](https://en.wikipedia.org/wiki/2b2t), and a huge amount of emergence that nobody designed or planned for. That is the quality I care about: a formal system whose consequences exceed the designer's first-order intentions because players bring values and memory into it.

The current Samsara simulation loop is fully GPU resident. The renderer is compute-only, using [sparse voxel octrees (tree64)](https://dubiousconst282.github.io/2024/10/03/voxel-ray-tracing/). The current (third) rewrite is in Python with [SlangPy](https://shader-slang.org/slangpy/). Python just handles orchestration while [Slang](https://shader-slang.org/) owns the GPU work. Earlier versions were in Zig and WebGPU-shaped stacks. I expect the implementation to keep changing as languages like [Bend](https://github.com/HigherOrderCO/Bend) (see [HVM](https://github.com/HigherOrderCO/HVM)) improve. The shape of the system remains the more important part: we want worlds that are fast, inspectable, and deterministic enough for agents and humans to search them together.

The engine has a `.traj` language and a unified `Action` set for deterministic playback, screenshots, state dumps, and metric queries. The same path runs in a window for a human or headlessly for an agent. Battery Arena can train policies via self-play, replay fights, run live play, and produce validation artifacts. Recent 512-environment headless runs reach roughly 60,000 actor-control steps/s.

GPU residency matters because the game itself is the thing being searched. Most engines keep gameplay authority on the CPU and use the GPU for rendering plus a few accelerators. That works for shipping normal games, but it fights vectorized training. The CPU only handles the outside world, essentially just i/o. One arena can become hundreds of arenas, and one ruleset can be evaluated across many seeds without dragging state through host memory every tick. The [Terra](https://github.com/PolyhedralDev/Terra) port is the same lesson in miniature: world generation gets roughly 200x faster when the work moves out of Minecraft's Java path and into parallel GPU code.

Trajectory-Driven Development came from the same requirement. A human can play the game, record the input stream, and turn it into a replayable `.traj` file. An agent can run that trajectory headlessly, capture screenshots, query state, and compare the result after a code change. A bug report becomes a causal path through the world. Engine work gets a stable verification loop: replay the same situation, inspect the same moment, and check whether the behavior changed in the intended direction.

The action ontology supports that loop. Player input, agent input, debug tools, and replay files share a clear `Action` type. The engine can reconstruct what happened, who requested it, what actually occurred, and which consequences followed. Humans, bots, tests, and tools stay on the same path.

Self-querying is the most important layer of legibility, because the engine needs composable data about game state in order to reason effectively about what occurs in games. Did bots rescue allies more reliably? Did a movement change create evasive pressure? Did a terrain change create useful cover? Samsara already has probes for focus fire, blocked shots, rescue attempts, and wall contact. As those probes increasingly expand, composability will become the most important thing.

It is a small arena where policies fight with bow-like combat and a battery resource. Positive battery makes attacks stronger. Negative battery makes heals stronger. Shooting drains toward the healing side. Healing charges toward the fighting side. The mechanic tries to create role cycling from the physics of the game. One version is team-based; another lets agents output continuous alignment toward other agents, so teams can emerge from affinity choices.

The arena is intentionally narrow. In one run I can train policies, replay fights, compare checkpoints, and ask whether focus fire appeared. Then I can change the rules. This is small enough to understand and large enough to touch the real problem: the engine has to make behavior legible before agents can improve it.

**The larger pattern is: The game has an inner loop and an outer loop. In the inner loop, players or in-game agents pursue goals under given rules. They should play the game as hard as the game allows and maximize their objectives. The outer loop watches what those attempts produce and changes the game itself. For differentiable substrates, we can use gradient descent, and for ones that are discrete, we can use evolution. Interestingness cannot be formalized once and then maximized forever, but novelty can still help the outer loop find regions worth showing to a human.**

Minecraft already has multiplayer, entities, worlds, mod distribution, and years of social proof. A mod lets me test movement+combat, multiplayer, and whether a mechanic feels alive. Testing inside that existing reality is much cheaper than rebuilding every primitive first. Coding agents make it trivial to port that logic back into my game engine. Given AI improvement rates, waiting seems fruitful here.

Battery arena, world generation, different game modules/scenes, and the minecraft mockups all work on different levels of friction to solve problems on different layers of the stack. The main challenge will be integrating those modules into a coherent whole. There is an uncomfortable but fun amount of uncertainty in this. A lot of software now feels temporary due to increasing AI capability. The work that still feels worth doing sits closer to ontology and scaffolding. 

That is the current shape of Samsara: an engine where play produces evidence, evidence changes the rules, and the changed rules can be played again. The stack will definitely change in the future, but hopefully we'll converge enough to diverge forever :)
